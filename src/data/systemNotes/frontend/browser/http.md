# HTTP와 REST API

## HTTP란?

**HyperText Transfer Protocol**의 약자로, **웹에서 클라이언트와 서버 간 데이터를 주고받기 위한 프로토콜**입니다.

원래는 HTML 문서를 전송하기 위해 설계되었지만, 현재는 텍스트, 이미지, 영상, JSON, XML 등 거의 모든 형태의 데이터를 전송합니다. 웹 브라우저와 서버 간 통신뿐 아니라 서버 간 통신, 모바일 앱과 서버 간 통신에도 HTTP가 사용됩니다.

### HTTP의 특징

| 특징 | 설명 |
|------|------|
| **클라이언트-서버 구조** | 요청(Request)과 응답(Response)으로 분리 |
| **무상태(Stateless)** | 서버가 클라이언트 상태를 저장하지 않음 |
| **비연결성(Connectionless)** | 요청-응답 후 연결 종료 (HTTP/1.0 기준) |
| **확장 가능** | 헤더를 통해 기능 확장 가능 |

### 무상태(Stateless)의 의미

서버는 각 요청을 독립적으로 처리하며, 이전 요청의 정보를 기억하지 않습니다. 첫 번째 요청에서 로그인했더라도, 두 번째 요청에서 서버는 이를 모릅니다.

**장점**: 서버 확장성이 좋습니다. 아무 서버나 요청을 처리할 수 있어 수평 확장(Scale-out)이 쉽습니다.

**단점**: 매 요청마다 인증 정보를 보내야 합니다. 이를 해결하기 위해 쿠키, 세션, JWT 토큰 등을 사용합니다.

### 비연결성(Connectionless)

HTTP/1.0에서는 요청-응답 후 TCP 연결을 끊었습니다. 매번 연결을 새로 맺는 오버헤드가 컸습니다. HTTP/1.1부터 **Keep-Alive**가 기본값이 되어 일정 시간 연결을 유지합니다. 여러 요청을 하나의 연결로 처리할 수 있어 성능이 개선되었습니다.

---

## HTTP 버전별 특징

| 버전 | 특징 |
|------|------|
| **HTTP/1.0** | 요청마다 새 연결. 비효율적 |
| **HTTP/1.1** | Keep-Alive 기본, 파이프라이닝 |
| **HTTP/2** | 멀티플렉싱, 헤더 압축, 서버 푸시 |
| **HTTP/3** | UDP 기반(QUIC), 연결 설정 빠름 |

HTTP/1.1에서는 앞 요청이 완료되어야 다음 요청을 처리하는 **HOL(Head-of-Line) Blocking** 문제가 있습니다. HTTP/2는 **멀티플렉싱**으로 하나의 연결에서 여러 요청/응답을 동시에 처리하고, **헤더 압축**으로 오버헤드를 줄였습니다. HTTP/3는 TCP 대신 **QUIC(UDP 기반)**을 사용하여 연결 설정 지연을 없앴습니다.

## HTTPS

### HTTPS란?

**HTTP + TLS(SSL)**로, HTTP 통신을 암호화한 프로토콜입니다. 기본 포트는 443입니다.

HTTP는 데이터를 평문으로 전송합니다. 네트워크 중간에서 누군가 패킷을 가로채면 내용을 그대로 볼 수 있습니다. 로그인 정보, 결제 정보 등 민감한 데이터가 노출될 수 있습니다. HTTPS는 TLS(Transport Layer Security)로 데이터를 암호화하여 이를 방지합니다.

### HTTP vs HTTPS

| 구분 | HTTP | HTTPS |
|------|------|-------|
| 포트 | 80 | 443 |
| 암호화 | 없음 (평문) | TLS로 암호화 |
| 인증서 | 불필요 | 필요 (CA 발급) |
| 속도 | 약간 빠름 | 핸드셰이크 오버헤드 |
| SEO | 불리 | 유리 (Google 순위 요소) |
| 브라우저 | "주의 요함" 경고 | 자물쇠 아이콘 |

### HTTPS가 제공하는 것

| 기능 | 설명 |
|------|------|
| **기밀성 (Confidentiality)** | 암호화로 도청 방지. 중간에서 봐도 내용 모름 |
| **무결성 (Integrity)** | 데이터 변조 감지. 중간에서 수정하면 알 수 있음 |
| **인증 (Authentication)** | 인증서로 서버 신원 확인. 피싱 사이트 방지 |

### 대칭키와 비대칭키 암호화

**대칭키 암호화**: 암호화와 복호화에 같은 키 사용. 빠르지만 키를 안전하게 공유하기 어렵습니다.

**비대칭키 암호화**: 공개키로 암호화, 개인키로 복호화 (또는 반대). 키 공유 문제 해결. 느리지만 안전합니다.

HTTPS는 **둘을 조합**합니다. 처음에 비대칭키로 안전하게 대칭키를 교환하고, 이후 통신은 빠른 대칭키로 암호화합니다.

### TLS 핸드셰이크 (간략화)

```
1. Client Hello: 클라이언트가 지원하는 암호화 방식 전송
2. Server Hello: 서버가 선택한 암호화 방식 + 인증서 전송
3. 인증서 검증: 클라이언트가 CA를 통해 인증서 유효성 확인
4. 키 교환: 대칭키 생성을 위한 정보 교환
5. 암호화 통신 시작: 대칭키로 데이터 암호화
```

이 과정이 추가되어 HTTP보다 연결 설정이 느립니다. HTTP/2, HTTP/3, TLS 1.3 등은 이 오버헤드를 줄이는 최적화를 포함합니다.

### SSL 인증서

**CA(Certificate Authority)**가 발급하는 디지털 인증서입니다. 서버의 신원을 보증합니다.

| 구성 요소 | 설명 |
|----------|------|
| 도메인 정보 | 인증서가 유효한 도메인 |
| 공개키 | 서버의 공개키 |
| 발급자 | CA 정보 |
| 유효 기간 | 만료일 |
| 디지털 서명 | CA의 서명 (위조 방지) |

브라우저는 내장된 신뢰할 수 있는 CA 목록과 대조하여 인증서를 검증합니다. 검증 실패 시 경고를 표시합니다.

### 인증서 종류

| 종류 | 검증 수준 | 발급 시간 | 비용 |
|------|----------|----------|------|
| **DV (Domain Validation)** | 도메인 소유권만 | 즉시~몇 분 | 무료~저가 |
| **OV (Organization Validation)** | 조직 실체 확인 | 며칠 | 중간 |
| **EV (Extended Validation)** | 엄격한 심사 | 몇 주 | 고가 |

Let's Encrypt는 무료 DV 인증서를 제공하여 HTTPS 보급에 크게 기여했습니다.

### HTTPS가 필수인 이유

**보안**: 로그인, 결제 등 민감한 정보 보호. 중간자 공격(MITM) 방지.

**브라우저 정책**: Chrome 등 주요 브라우저가 HTTP 사이트에 "주의 요함" 경고 표시. Service Worker, Geolocation 등 일부 API는 HTTPS에서만 사용 가능.

**SEO**: Google이 HTTPS를 검색 순위 요소로 사용. HTTP 사이트는 순위에서 불리.

**신뢰성**: 사용자가 자물쇠 아이콘으로 안전한 사이트임을 인식.

## HTTP 메시지 구조

HTTP 메시지는 **시작 라인, 헤더, 빈 줄, 본문**으로 구성됩니다.

**요청**: `GET /api/users HTTP/1.1` (메서드, URL, 버전) + 헤더 + 본문
**응답**: `HTTP/1.1 200 OK` (버전, 상태코드, 메시지) + 헤더 + 본문

헤더는 `키: 값` 형태의 메타데이터(Content-Type, Authorization 등)를 담고, 본문은 실제 전송 데이터를 담습니다.

## HTTP 메서드

HTTP 메서드는 **리소스에 대해 수행할 동작**을 나타냅니다. 같은 URL이라도 메서드에 따라 다른 동작을 수행합니다.

### 주요 메서드

| 메서드 | 용도 | 요청 본문 | 응답 본문 | 멱등성 | 안전 |
|--------|------|----------|----------|--------|------|
| **GET** | 리소스 조회 | X | O | O | O |
| **POST** | 리소스 생성, 처리 | O | O | X | X |
| **PUT** | 리소스 전체 교체 | O | O | O | X |
| **PATCH** | 리소스 부분 수정 | O | O | X | X |
| **DELETE** | 리소스 삭제 | X | △ | O | X |
| **HEAD** | GET과 동일하나 본문 없음 | X | X | O | O |
| **OPTIONS** | 지원 메서드 확인 | X | O | O | O |

### GET

**리소스를 조회**합니다. 서버의 데이터를 변경하지 않아야 합니다. 쿼리 파라미터로 필터링, 정렬, 페이지네이션 등을 수행합니다.

```
GET /api/users?page=1&limit=10
GET /api/users/123
```

GET 요청은 **캐시 가능**합니다. 브라우저나 CDN이 응답을 저장하고 재사용할 수 있습니다.

### POST

**새 리소스를 생성**하거나 **특정 프로세스를 처리**합니다. 요청할 때마다 새 리소스가 생성될 수 있어 멱등하지 않습니다.

```
POST /api/users
Body: { "name": "Kim", "email": "kim@example.com" }
```

POST는 리소스 생성 외에도 로그인, 결제 처리, 복잡한 검색 등 다양한 용도로 사용됩니다. 만능이지만, 의미가 명확한 다른 메서드가 있다면 그것을 사용하는 것이 좋습니다.

### PUT

**리소스 전체를 교체**합니다. 해당 리소스가 없으면 새로 생성합니다. 클라이언트가 리소스의 전체 표현을 알고 있어야 합니다.

```
PUT /api/users/123
Body: { "name": "Lee", "email": "lee@example.com", "age": 30 }
```

**주의**: PUT은 부분 수정이 아닙니다. 전송하지 않은 필드는 삭제되거나 기본값으로 설정될 수 있습니다.

### PATCH

**리소스 일부를 수정**합니다. 변경할 필드만 전송합니다.

```
PATCH /api/users/123
Body: { "name": "Park" }  // name만 변경, 나머지 유지
```

PUT과의 차이: PUT은 "이것으로 교체해라", PATCH는 "이 부분만 바꿔라"입니다.

### DELETE

**리소스를 삭제**합니다. 일반적으로 본문 없이 사용합니다.

```
DELETE /api/users/123
```

### 안전한 메서드 (Safe Methods)

**서버의 상태를 변경하지 않는 메서드**입니다. GET, HEAD, OPTIONS가 해당합니다. 여러 번 호출해도 서버 데이터가 변하지 않습니다. 캐시, 프리페치 등에 안전하게 사용할 수 있습니다.

### 멱등성 (Idempotency)

**동일한 요청을 여러 번 보내도 결과가 같은 성질**입니다. GET, PUT, DELETE가 멱등합니다.

| 메서드 | 멱등성 | 이유 |
|--------|--------|------|
| GET | O | 조회만 하므로 결과 동일 |
| PUT | O | 같은 데이터로 덮어쓰므로 결과 동일 |
| DELETE | O | 이미 삭제된 것을 다시 삭제해도 결과 동일 |
| POST | X | 매번 새 리소스 생성 가능 |
| PATCH | X | 상대적 연산(count +1 등)이면 결과 다름 |

멱등성은 **네트워크 오류 시 재시도**에 중요합니다. 멱등한 요청은 응답을 받지 못해도 안전하게 재시도할 수 있습니다.

## HTTP 상태 코드

서버가 **요청 처리 결과를 알려주는 3자리 숫자**입니다.

### 상태 코드 분류

| 범위 | 분류 | 의미 |
|------|------|------|
| **1xx** | Informational | 요청 수신, 처리 중 |
| **2xx** | Success | 요청 성공 |
| **3xx** | Redirection | 추가 동작 필요 (리다이렉트) |
| **4xx** | Client Error | 클라이언트 오류 |
| **5xx** | Server Error | 서버 오류 |

### 자주 사용하는 상태 코드

| 코드 | 의미 | 설명 |
|------|------|------|
| **200** | OK | 성공 |
| **201** | Created | 리소스 생성 성공 |
| **204** | No Content | 성공, 응답 본문 없음 |
| **301** | Moved Permanently | 영구 리다이렉트 |
| **304** | Not Modified | 캐시 사용 |
| **400** | Bad Request | 잘못된 요청 |
| **401** | Unauthorized | 인증 필요 |
| **403** | Forbidden | 권한 없음 |
| **404** | Not Found | 리소스 없음 |
| **409** | Conflict | 충돌 (중복 등) |
| **429** | Too Many Requests | Rate Limit 초과 |
| **500** | Internal Server Error | 서버 오류 |
| **502** | Bad Gateway | 게이트웨이 오류 |
| **503** | Service Unavailable | 서비스 중단 |

### 401 vs 403

| 401 Unauthorized | 403 Forbidden |
|------------------|---------------|
| "누구세요?" | "당신은 안 돼요" |
| 인증(Authentication) 실패 | 인가(Authorization) 실패 |
| 로그인 안 함 또는 토큰 만료 | 로그인은 됐지만 권한 없음 |

## REST API

### REST란?

**REpresentational State Transfer**의 약자로, **웹 API를 설계하는 아키텍처 스타일**입니다. Roy Fielding이 2000년 박사 논문에서 제안했습니다.

REST는 프로토콜이나 표준이 아닌 **설계 원칙의 모음**입니다. 이 원칙을 따르는 API를 RESTful API라고 합니다.

### REST의 핵심 개념

**리소스(Resource)**: 서버가 관리하는 모든 것. 사용자, 게시글, 주문 등. URI로 식별합니다.

**표현(Representation)**: 리소스의 상태를 나타내는 데이터. JSON, XML, HTML 등 다양한 형태로 표현할 수 있습니다.

**상태 전이(State Transfer)**: 클라이언트가 표현을 통해 서버의 리소스 상태를 변경합니다.

### REST 원칙 (6가지 제약 조건)

| 원칙 | 설명 |
|------|------|
| **클라이언트-서버 분리** | UI와 데이터 저장을 분리. 독립적 진화 가능 |
| **무상태** | 서버가 클라이언트 상태 저장 안 함. 요청에 필요한 모든 정보 포함 |
| **캐시 가능** | 응답에 캐시 가능 여부 명시. 성능 향상 |
| **계층화 시스템** | 클라이언트가 직접 서버인지 중간 서버인지 모름. 로드밸런서, 프록시 등 |
| **균일한 인터페이스** | 일관된 방식으로 리소스 조작. REST의 핵심 |
| **코드 온 디맨드** | (선택) 서버가 클라이언트에 코드 전송 가능 |

### 균일한 인터페이스 (Uniform Interface)

REST의 가장 중요한 원칙입니다. 4가지 제약으로 구성됩니다.

| 제약 | 설명 |
|------|------|
| **리소스 식별** | URI로 리소스를 고유하게 식별 |
| **표현을 통한 조작** | 리소스 자체가 아닌 표현(JSON 등)을 주고받음 |
| **자기 서술적 메시지** | 메시지만 보고 무엇을 할지 알 수 있음 |
| **HATEOAS** | 응답에 다음 가능한 동작의 링크 포함 |

## RESTful API 설계

### URI 설계 원칙

| 원칙 | 좋은 예 | 나쁜 예 |
|------|--------|--------|
| 리소스는 명사 | `GET /users` | `GET /getUsers` |
| 복수형 사용 | `/users`, `/posts` | `/user`, `/post` |
| 계층 관계 표현 | `/users/123/posts` | - |
| 필터링은 쿼리 | `/users?status=active` | `/users/active` |

동사는 HTTP 메서드가 담당하고, URI에는 리소스(명사)만 사용합니다.

### CRUD와 HTTP 메서드 매핑

| 동작 | HTTP 메서드 | URI 예시 | 응답 코드 |
|------|------------|----------|----------|
| 목록 조회 | GET | /users | 200 |
| 단건 조회 | GET | /users/123 | 200, 404 |
| 생성 | POST | /users | 201, 400 |
| 전체 수정 | PUT | /users/123 | 200, 404 |
| 부분 수정 | PATCH | /users/123 | 200, 404 |
| 삭제 | DELETE | /users/123 | 204, 404 |

### URI 설계 안티패턴

```
❌ GET /getUser/123              동사 사용
❌ POST /users/123/delete        메서드 오용 (DELETE 사용)
❌ GET /users/search/kim         동사 사용 (/users?name=kim)
❌ GET /api/v1/user/list         불필요한 경로 (/users)
```

### 응답 설계

성공과 에러 응답 구조를 일관되게 유지합니다. 성공 시 `data` 필드에 결과를, 에러 시 `error` 필드에 코드와 메시지를 담는 방식이 일반적입니다. 일관된 구조는 클라이언트 처리를 단순화합니다.

## REST의 한계와 대안

| 한계 | 설명 |
|------|------|
| **Over-fetching** | 필요 이상의 데이터를 받음 |
| **Under-fetching** | 여러 번 요청해야 필요한 데이터 수집 |
| **N+1 요청** | 목록 조회 후 각 항목 상세 조회 |

**GraphQL**은 클라이언트가 필요한 필드만 선택하여 Over/Under-fetching을 해결합니다. 하지만 학습 곡선이 있고 캐싱이 복잡합니다. 단순한 CRUD는 REST, 복잡한 데이터 관계는 GraphQL이 적합합니다.

## 면접 예상 질문

**Q. HTTP의 특징?**

클라이언트-서버 구조로 요청/응답이 분리되고, 무상태(Stateless)라 서버가 클라이언트 상태를 저장하지 않습니다. 무상태 덕분에 서버 확장이 쉽지만, 매 요청마다 인증 정보가 필요하여 쿠키, 세션, JWT 등을 사용합니다.

**Q. HTTP와 HTTPS의 차이?**

HTTPS는 HTTP에 TLS 암호화를 추가한 것입니다. HTTP는 평문 통신이라 도청이 가능하고, HTTPS는 암호화하여 기밀성, 무결성, 인증을 제공합니다. HTTPS는 인증서가 필요하고, 핸드셰이크 오버헤드가 있지만, 보안, SEO, 브라우저 정책상 필수입니다.

**Q. TLS 핸드셰이크 과정?**

클라이언트가 지원하는 암호화 방식을 보내고, 서버가 선택한 방식과 인증서를 응답합니다. 클라이언트가 CA를 통해 인증서를 검증하고, 비대칭키로 대칭키 교환 정보를 주고받습니다. 이후 대칭키로 암호화된 통신이 시작됩니다.

**Q. GET과 POST의 차이?**

GET은 리소스 조회용으로 멱등하고 캐시 가능합니다. 데이터는 URL 쿼리 파라미터로 전달합니다. POST는 리소스 생성이나 처리용으로 멱등하지 않고 캐시되지 않습니다. 데이터는 요청 본문으로 전달합니다.

**Q. PUT과 PATCH의 차이?**

PUT은 리소스 전체를 교체합니다. 전송하지 않은 필드는 삭제될 수 있습니다. PATCH는 리소스 일부만 수정합니다. 변경할 필드만 전송하고 나머지는 유지됩니다. PUT은 멱등하고 PATCH는 멱등하지 않을 수 있습니다.

**Q. 멱등성이란?**

동일한 요청을 여러 번 보내도 결과가 같은 성질입니다. GET, PUT, DELETE가 멱등합니다. 네트워크 오류로 응답을 받지 못했을 때 멱등한 요청은 안전하게 재시도할 수 있습니다.

**Q. 401과 403의 차이?**

401은 인증(Authentication) 실패로 "누구세요?"입니다. 로그인하지 않았거나 토큰이 만료된 경우입니다. 403은 인가(Authorization) 실패로 "권한 없음"입니다. 인증은 됐지만 해당 리소스에 접근할 권한이 없는 경우입니다.

**Q. REST란?**

웹 API를 설계하는 아키텍처 스타일입니다. 리소스를 URI로 식별하고, HTTP 메서드로 동작을 정의합니다. 무상태, 캐시 가능, 균일한 인터페이스 등의 원칙을 따릅니다. 이 원칙을 따르는 API를 RESTful API라고 합니다.

**Q. RESTful API 설계 원칙?**

URI는 리소스(명사)로 표현하고 복수형을 사용합니다. 동사는 HTTP 메서드가 담당합니다. 계층 관계는 슬래시로, 필터링은 쿼리 파라미터로 표현합니다. `/users/123/posts`처럼 설계하고, `/getUser` 같은 동사 사용은 피합니다.
