# HTTP 캐시

## 개요

브라우저가 서버에서 받은 리소스를 로컬에 저장하여, 동일한 요청 시 네트워크 통신 없이 재사용하는 메커니즘입니다.
- 리소스란 서버에서 보내는 모든 정보(HTML, CSS, JS, 미디어, 폰트, 이미지 등등)
- 캐시 전략은 서버에서 이 데이터를 어떻게 캐싱 할 지 Cache-Control을 정해서 보내주면 브라우저에서 그 전략에 따라 캐싱하는 것(브라우저 설정으로 무시할 수도 있다)

```
첫 요청: 클라이언트 → 서버 → 리소스 + 캐시 헤더 응답 → 브라우저 캐시 저장
재요청: 브라우저 캐시에서 바로 사용 (유효 시간 내)
```

## Cache-Control 헤더

캐시 동작을 제어하는 핵심 헤더입니다.

| 값 | 설명 |
|----|------|
| max-age=초 | 캐시 유효 시간 (초 단위) |
| no-cache | 캐시 저장 O, 사용 전 서버에 검증 필수 |
| no-store | 캐시 저장 X (민감한 정보) |
| public | CDN 등 공유 캐시에 저장 가능 |
| private | 브라우저에만 저장, 공유 캐시 저장 불가 |
| must-revalidate | 만료 후 반드시 서버 검증 필요 |

### no-cache vs no-store

| 구분 | no-cache | no-store |
|------|----------|----------|
| 캐시 저장 | O | X |
| 사용 조건 | 매번 서버 검증 후 사용 | 저장 자체를 안 함 |
| 용도 | 항상 최신 데이터 필요 | 민감한 정보 (개인정보, 결제 등) |

## 캐시 검증 (Validation)

캐시 유효 시간이 지났을 때, 서버에 데이터가 변경되었는지 확인하는 과정입니다.

### 검증 방식 비교

| 구분 | Last-Modified | ETag |
|------|---------------|------|
| 검증 기준 | 파일 수정 시간 | 파일 해시값 또는 버전 |
| 요청 헤더 | If-Modified-Since | If-None-Match |
| 정밀도 | 초 단위 (1초 미만 감지 불가) | 정확함 |
| 한계 | 내용 같아도 시간 바뀌면 재전송 | 없음 |

### 검증 흐름

```
1. 클라이언트: 캐시 만료됨, 서버에 검증 요청
   → If-None-Match: "abc123" (또는 If-Modified-Since)

2. 서버: ETag 비교
   → 같으면: 304 Not Modified (본문 없음)
   → 다르면: 200 OK + 새 데이터

3. 클라이언트: 304면 캐시 재사용, 200이면 새 데이터 저장
```

**핵심:** 304 응답은 본문이 없어서 네트워크 비용 절약

## 브라우저 캐시 저장 위치

| 위치 | 특징 | 용도 |
|------|------|------|
| Memory Cache | 메모리에 저장, 탭 닫으면 삭제 | 현재 세션에서 자주 쓰는 리소스 |
| Disk Cache | 디스크에 저장, 브라우저 종료 후에도 유지 | 큰 파일, 장기 캐시 |

브라우저가 자동으로 판단하여 저장 위치 결정

## 실무 캐시 전략

### 정적 파일 (JS, CSS, 이미지)

```
Cache-Control: public, max-age=31536000, immutable
```

- 1년 캐시 (31536000초)
- 파일명에 해시 포함하여 변경 시 URL 자체가 바뀜

```html
<!-- 빌드 시 해시가 붙음 -->
<script src="/app.a1b2c3d4.js"></script>
```

### HTML 문서

```
Cache-Control: no-cache
```

- 항상 서버에 검증 후 사용
- HTML이 바뀌어야 새 JS/CSS 파일 URL을 받을 수 있음

### API 응답

```
Cache-Control: private, no-cache
```

- 개인화된 데이터는 private
- 실시간성 필요하면 no-cache 또는 짧은 max-age

## 캐시 무효화

캐시된 리소스를 강제로 새로 받게 하는 방법

| 방법 | 설명 |
|------|------|
| 파일명 해시 | `app.abc123.js` → 파일 변경 시 해시 변경 |
| 쿼리스트링 | `app.js?v=2` → 버전 변경 시 URL 변경 |
| Cache-Control 변경 | max-age를 짧게 설정 |

**권장:** 파일명 해시 방식 (Webpack, Vite 등 빌드 도구가 자동 처리)

## 요약 표

| 상황 | Cache-Control | 검증 헤더 |
|------|---------------|-----------|
| 정적 파일 (해시 있음) | max-age=31536000, immutable | 불필요 |
| HTML | no-cache | ETag |
| API (개인화) | private, no-cache | ETag |
| 민감한 정보 | no-store | 불필요 |

## Study

**Q. no-cache와 no-store 차이?**

no-cache는 캐시에 저장하지만 사용 전 서버에 검증을 받아야 합니다. no-store는 캐시에 저장 자체를 하지 않습니다. 민감한 정보는 no-store, 항상 최신 데이터가 필요한 경우는 no-cache를 사용합니다.

**Q. ETag가 Last-Modified보다 좋은 이유?**

Last-Modified는 초 단위라 1초 미만 변경을 감지 못하고, 파일을 수정했다 되돌려도 시간이 바뀌어 불필요한 재전송이 발생합니다. ETag는 파일 내용 기반 해시라 실제 변경 여부를 정확히 판단할 수 있습니다.

**Q. 304 Not Modified 응답의 의미?**

캐시가 만료되어 서버에 검증 요청을 보냈을 때, 서버의 데이터가 변경되지 않았음을 의미합니다. 본문 없이 헤더만 응답하므로 네트워크 비용을 절약하고, 클라이언트는 기존 캐시를 재사용합니다.

**Q. 프론트엔드 빌드 시 캐시 전략?**

정적 파일(JS, CSS)은 파일명에 해시를 붙여 장기 캐시(1년)하고, HTML은 no-cache로 설정합니다. 파일이 변경되면 해시가 바뀌어 URL 자체가 달라지므로 자동으로 새 파일을 받게 됩니다.
