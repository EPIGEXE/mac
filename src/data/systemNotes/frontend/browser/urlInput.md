# URL 입력부터 화면이 보이기까지

## 전체 흐름

```
URL 입력 → DNS 조회 → TCP 연결 → (TLS 핸드셰이크) → HTTP 요청/응답 → 브라우저 렌더링
```

## 1. URL 입력 및 해석

`https://example.com/path?query=1`을 입력하면:

| 구성 요소 | 값 | 설명 |
|-----------|-----|------|
| 프로토콜 | https | 보안 연결 (TLS 사용) |
| 호스트 | example.com | DNS로 IP 변환 필요 |
| 포트 | 443 (생략됨) | HTTPS 기본 포트 |
| 경로 | /path | 요청할 리소스 위치 |
| 쿼리스트링 | ?query=1 | 서버에 전달할 데이터 |

## 2. DNS 조회

호스트명(example.com)을 IP 주소로 변환합니다.

### 조회 순서

```
브라우저 캐시 → OS 캐시 → 라우터 캐시 → ISP DNS → 재귀적 DNS 조회
```

### 재귀적 DNS 조회 (캐시에 없는 경우)

```
클라이언트 → 루트 DNS → .com TLD DNS → example.com 권한 DNS → IP 반환
```

각 단계의 결과는 캐시되어 다음 요청 시 재사용됩니다.

## 3. TCP 연결 (3-Way Handshake)

IP 주소를 얻으면 서버와 TCP 연결을 수립합니다.

```
클라이언트                    서버
    |                          |
    |-------- SYN ------------>|  "연결하고 싶어"
    |                          |
    |<------ SYN-ACK ----------|  "알겠어, 나도 준비됐어"
    |                          |
    |-------- ACK ------------>|  "확인, 연결 시작하자"
    |                          |
```

**목적:** 양쪽이 데이터를 주고받을 준비가 됐는지 확인

## 4. TLS 핸드셰이크 (HTTPS)

TCP 연결 후, HTTPS면 암호화 연결을 수립합니다.

```
클라이언트                              서버
    |                                    |
    |------ Client Hello --------------->|  지원하는 암호화 방식 전송
    |                                    |
    |<----- Server Hello + 인증서 -------|  선택한 암호화 방식 + 인증서
    |                                    |
    |  (인증서 검증)                       |
    |                                    |
    |------ 키 교환 -------------------->|  세션 키 생성을 위한 정보
    |                                    |
    |<===== 암호화된 통신 시작 ===========>|
```

**목적:** 
- 서버가 진짜 example.com인지 인증서로 확인
- 이후 통신에 사용할 대칭키(세션 키) 안전하게 교환
- 중간자 공격 방지

## 5. HTTP 요청 전송

암호화 연결이 수립되면 HTTP 요청을 보냅니다.

```http
GET /path?query=1 HTTP/1.1
Host: example.com
User-Agent: Chrome/120.0
Accept: text/html
Cookie: session=abc123
```

## 6. HTTP 응답 수신

서버가 요청을 처리하고 응답합니다.

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Cache-Control: no-cache

<!DOCTYPE html>
<html>...
```

## 7. 브라우저 렌더링

응답받은 HTML을 화면에 그립니다.

```
HTML 파싱 → DOM 생성
                      → 렌더 트리 → 레이아웃 → 페인트 → 컴포지팅
CSS 파싱 → CSSOM 생성
```

(상세 내용은 브라우저 렌더링 문서 참고)

## 전체 과정 요약

| 단계 | 하는 일 | 결과 |
|------|---------|------|
| URL 해석 | 프로토콜, 호스트, 포트, 경로 파싱 | 요청 정보 준비 |
| DNS 조회 | 도메인 → IP 변환 | 93.184.216.34 |
| TCP 연결 | 3-Way Handshake | 연결 수립 |
| TLS 핸드셰이크 | 인증서 확인, 키 교환 | 암호화 채널 |
| HTTP 요청 | GET 요청 전송 | 요청 완료 |
| HTTP 응답 | HTML, CSS, JS 수신 | 리소스 확보 |
| 렌더링 | DOM/CSSOM → 화면 그리기 | 화면 표시 |

## Study

**Q. 브라우저에 URL을 입력하면 어떤 일이 일어나나요?**

URL을 파싱하고, DNS로 도메인을 IP로 변환합니다. 그 IP로 TCP 3-Way Handshake를 통해 연결하고, HTTPS면 TLS 핸드셰이크로 암호화 채널을 만듭니다. 그 후 HTTP 요청을 보내고 응답으로 HTML을 받으면, 브라우저가 DOM과 CSSOM을 만들어 렌더 트리를 구성하고 레이아웃, 페인트, 컴포지팅을 거쳐 화면에 그립니다.

**Q. 3-Way Handshake가 필요한 이유?**

TCP는 신뢰성 있는 연결을 보장해야 합니다. SYN-SYN/ACK-ACK 과정을 통해 클라이언트와 서버 양쪽이 데이터를 보내고 받을 준비가 됐는지 확인합니다. 이 과정 없이 바로 데이터를 보내면 상대방이 받을 준비가 안 됐을 수 있습니다.

**Q. HTTPS가 HTTP보다 안전한 이유?**

HTTPS는 TLS 핸드셰이크를 통해 서버 인증서를 검증하고, 세션 키를 교환해서 이후 모든 통신을 암호화합니다. 중간자가 패킷을 가로채도 내용을 볼 수 없고, 서버를 사칭하는 것도 인증서 검증으로 방지됩니다.
