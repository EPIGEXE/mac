# 데드락 (Deadlock, 교착상태)

## 데드락이란?

**두 개 이상의 프로세스(또는 스레드)가 서로 상대방이 가진 자원을 기다리며 무한히 대기하는 상태**입니다. 어떤 프로세스도 진행할 수 없어 시스템이 멈춘 것처럼 보입니다.

```
┌─────────────┐         ┌─────────────┐
│  Process A  │         │  Process B  │
│             │         │             │
│ Resource 1  │◄───────►│ Resource 2  │
│   보유 중    │  서로    │   보유 중    │
│             │  대기    │             │
│ Resource 2  │         │ Resource 1  │
│   대기 중    │         │   대기 중    │
└─────────────┘         └─────────────┘
```

**예시 상황:**

```
1. Process A가 Resource 1을 획득
2. Process B가 Resource 2를 획득
3. Process A가 Resource 2를 요청 → B가 보유 중이라 대기
4. Process B가 Resource 1을 요청 → A가 보유 중이라 대기
5. 둘 다 영원히 대기 (Deadlock!)
```

---

## 데드락 발생 조건

다음 **4가지 조건이 모두 만족**할 때 데드락이 발생합니다. 하나라도 성립하지 않으면 데드락은 발생하지 않습니다.

**1. 상호 배제 (Mutual Exclusion)**

자원은 한 번에 하나의 프로세스만 사용할 수 있습니다. 다른 프로세스가 사용 중이면 반드시 대기해야 합니다.

```
Resource X: [Process A 사용 중]
Process B: "X 필요함" → 대기
```

**2. 점유 대기 (Hold and Wait)**

자원을 최소 하나 보유한 상태에서 다른 프로세스가 가진 자원을 추가로 기다립니다.

```
Process A: Resource 1 보유 + Resource 2 대기
```

**3. 비선점 (No Preemption)**

다른 프로세스가 사용 중인 자원을 강제로 빼앗을 수 없습니다. 자원은 보유한 프로세스가 자발적으로 해제해야만 합니다.

```
Process A가 Resource 1 사용 중
→ OS가 강제로 빼앗을 수 없음
→ A가 스스로 반납할 때까지 대기
```

**4. 순환 대기 (Circular Wait)**

프로세스들이 순환 형태로 서로의 자원을 대기합니다.

```
P1 → P2 → P3 → P1 (순환)

P1: R1 보유, R2 대기
P2: R2 보유, R3 대기  
P3: R3 보유, R1 대기
```

---

## 자원 할당 그래프 (Resource Allocation Graph)

데드락을 시각적으로 표현하는 방법입니다.

- **프로세스**: 원(○)
- **자원**: 사각형(□), 내부 점은 인스턴스 수
- **요청 간선**: 프로세스 → 자원 (대기 중)
- **할당 간선**: 자원 → 프로세스 (보유 중)

```
데드락 없음:                    데드락 발생:
                              
  P1 ──→ R1 ──→ P2             P1 ──→ R1 ──→ P2
         │                           │       │
         ▼                           ▼       ▼
        R2                          R2 ──→ P1
                                   (사이클 존재!)
```

**사이클이 존재하면:**
- 자원당 인스턴스가 1개: 반드시 데드락
- 자원당 인스턴스가 여러 개: 데드락 가능성 있음 (반드시는 아님)

## 데드락 해결 방법

### 1. 예방 (Prevention)

**4가지 조건 중 하나 이상을 사전에 차단**하여 데드락 자체가 발생하지 않도록 합니다.

| 조건 | 예방 방법 | 문제점 |
|------|----------|--------|
| 상호 배제 | 공유 가능하게 설계 | 대부분의 자원은 본질적으로 공유 불가 |
| 점유 대기 | 필요한 자원을 한 번에 모두 요청 | 자원 낭비, 기아 가능 |
| 비선점 | 자원을 빼앗을 수 있게 허용 | 상태 저장/복구 어려움 |
| 순환 대기 | 자원에 순서 부여, 순서대로만 요청 | 자원 활용률 저하 |

**순환 대기 예방 예시:**

```
자원 순서: R1 < R2 < R3

규칙: 항상 낮은 번호 자원부터 요청

Process A: R1 획득 → R2 요청 (OK)
Process B: R2 획득 → R1 요청 (거부! 순서 위반)

→ 순환 발생 불가
```

### 2. 회피 (Avoidance)

**자원 요청 시 시스템이 안전한지 검사**하고, 데드락 가능성이 있으면 요청을 거부합니다.

**안전 상태 (Safe State):**

모든 프로세스가 데드락 없이 종료할 수 있는 실행 순서(안전 순서)가 존재하는 상태입니다.

```
안전 상태: 어떤 순서로든 모든 프로세스 완료 가능
불안전 상태: 데드락 가능성 있음 (반드시 발생은 아님)
```

**은행원 알고리즘 (Banker's Algorithm):**

은행이 대출 시 모든 고객이 최대 대출을 받아도 파산하지 않는지 확인하는 것과 유사합니다.

```
프로세스별 정보:
- Max: 최대 필요 자원
- Allocation: 현재 할당된 자원
- Need: 추가 필요 자원 (Max - Allocation)

시스템 정보:
- Available: 현재 사용 가능한 자원
```

**예시:**

```
자원 총량: 12개
Available: 3개

        Max  Allocation  Need
P0       10      5        5
P1        4      2        2
P2        9      2        7

안전 순서 찾기:
1. Available(3) >= Need(P1:2) → P1 실행 가능
2. P1 완료 → Available = 3 + 2 = 5
3. Available(5) >= Need(P0:5) → P0 실행 가능
4. P0 완료 → Available = 5 + 5 = 10
5. Available(10) >= Need(P2:7) → P2 실행 가능

안전 순서: P1 → P0 → P2 (안전 상태!)
```

**한계:**
- 프로세스가 미리 최대 자원 요구량을 알려야 함
- 프로세스 수와 자원 수가 고정되어야 함
- 오버헤드가 큼

### 3. 탐지 및 복구 (Detection & Recovery)

**데드락 발생을 허용하고, 주기적으로 탐지하여 복구**합니다.

**탐지 방법:**
- 자원 할당 그래프에서 사이클 탐지
- 은행원 알고리즘 변형으로 안전 상태 검사

**복구 방법:**

| 방법 | 설명 | 문제점 |
|------|------|--------|
| 프로세스 종료 | 데드락 프로세스 중 일부/전체 종료 | 작업 손실 |
| 자원 선점 | 프로세스로부터 자원 강제 회수 | 상태 복구 필요, 기아 가능 |
| 롤백 | 체크포인트로 되돌리기 | 오버헤드, 재실행 필요 |

**프로세스 종료 기준 (어떤 것을 종료할지):**
- 우선순위가 낮은 프로세스
- 실행 시간이 짧은 프로세스 (재실행 비용 적음)
- 사용 자원이 많은 프로세스 (해제 효과 큼)
- 남은 작업이 많은 프로세스
- 대화형보다 배치 프로세스 우선

### 4. 무시 (Ignorance) - 타조 알고리즘

**데드락을 무시하고, 발생 시 시스템을 재시작**합니다.

대부분의 운영체제(Windows, Linux)에서 사용하는 방식입니다. 데드락 발생 빈도가 낮고, 예방/회피/탐지 비용이 높을 때 현실적인 선택입니다.

## 데드락 vs 기아 vs 라이브락

| 구분 | 설명 |
|------|------|
| **데드락** | 서로 자원을 기다리며 영원히 대기 |
| **기아 (Starvation)** | 우선순위가 낮아 자원을 계속 얻지 못함 (다른 프로세스는 진행) |
| **라이브락 (Livelock)** | 상태는 계속 변하지만 실제 진행 없음 (서로 양보만 반복) |

**라이브락 예시:**

```
좁은 복도에서 두 사람이 마주침:
A: 오른쪽으로 비킴
B: 왼쪽으로 비킴 (같은 방향)
A: 왼쪽으로 비킴
B: 오른쪽으로 비킴 (또 같은 방향)
→ 계속 반복, 진행 없음
```

## 실제 시스템에서의 데드락

**데이터베이스:**

```sql
-- Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Lock on id=1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- Wait for id=2

-- Transaction 2
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- Lock on id=2
UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- Wait for id=1

-- Deadlock! DBMS가 탐지하여 하나를 롤백
```

**운영체제:**

- 파일 잠금
- 프린터/디스크 등 장치 할당
- 메모리 할당

**멀티스레드 프로그래밍:**

```c
// Thread 1
pthread_mutex_lock(&mutex_A);
pthread_mutex_lock(&mutex_B);  // Wait
// ...
pthread_mutex_unlock(&mutex_B);
pthread_mutex_unlock(&mutex_A);

// Thread 2
pthread_mutex_lock(&mutex_B);
pthread_mutex_lock(&mutex_A);  // Wait
// ...
pthread_mutex_unlock(&mutex_A);
pthread_mutex_unlock(&mutex_B);

// Deadlock!
```

**해결: 잠금 순서 일관성 유지**

```c
// 항상 mutex_A → mutex_B 순서로 잠금
// Thread 1, 2 모두 동일한 순서 사용
pthread_mutex_lock(&mutex_A);
pthread_mutex_lock(&mutex_B);
```

## 면접 예상 질문

**Q. 데드락이란?**

두 개 이상의 프로세스가 서로 상대방이 가진 자원을 기다리며 무한히 대기하는 상태입니다. 어떤 프로세스도 진행할 수 없어 시스템이 멈춘 것처럼 됩니다.

**Q. 데드락 발생 조건 4가지?**

상호 배제(한 번에 하나만 사용), 점유 대기(보유하면서 대기), 비선점(강제 회수 불가), 순환 대기(순환 형태로 대기)입니다. 4가지 모두 만족해야 데드락이 발생하며, 하나라도 깨면 데드락을 방지할 수 있습니다.

**Q. 데드락 해결 방법?**

예방(4가지 조건 중 하나 차단), 회피(은행원 알고리즘으로 안전 상태 유지), 탐지 및 복구(발생 후 탐지하여 프로세스 종료/자원 선점), 무시(타조 알고리즘, 발생 시 재시작)가 있습니다. 대부분의 OS는 무시 방식을 사용합니다.

**Q. 은행원 알고리즘이란?**

자원 요청 시 시스템이 안전 상태를 유지하는지 검사하여, 데드락 가능성이 있으면 요청을 거부하는 회피 알고리즘입니다. 모든 프로세스가 종료 가능한 안전 순서가 존재하면 안전 상태입니다. 프로세스가 최대 자원 요구량을 미리 알려야 하는 한계가 있습니다.

**Q. 데드락과 기아의 차이?**

데드락은 서로 자원을 기다리며 모든 관련 프로세스가 멈추는 상태입니다. 기아는 우선순위가 낮아 특정 프로세스만 자원을 얻지 못하고, 다른 프로세스는 정상 진행됩니다. 기아는 에이징(대기 시간에 따라 우선순위 상승)으로 해결합니다.

**Q. 실제 데드락 방지 방법?**

잠금 순서를 일관되게 유지하여 순환 대기를 방지합니다. 타임아웃을 설정하여 일정 시간 후 포기하고 재시도합니다. 가능하면 잠금을 피하고 락-프리 자료구조나 트랜잭션 메모리를 사용합니다.
