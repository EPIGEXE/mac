# IP와 주소 체계

## 왜 IP 주소가 필요한가?

MAC 주소만으로는 인터넷 규모의 통신이 불가능하다. MAC 주소는 48비트로 전 세계적으로 유일하지만, **평면적(flat)**이라서 계층 구조가 없다. `AA:BB:CC:DD:EE:FF`를 보고 "이 장치가 한국에 있는지 미국에 있는지" 알 방법이 없다.

- 전 세계 수십억 MAC 주소의 위치를 기억하는 것은 불가능
- 라우터가 "이 MAC은 어느 방향으로 보내야 하는지" 결정할 수 없음
- 새 장치가 추가되면 전 세계 라우터가 갱신되어야 함

**IP 주소**는 **계층적(hierarchical)** 구조로 이 문제를 해결한다. "서울시 강남구 123번지"처럼, 네트워크 부분과 호스트 부분으로 나뉘어 있어서 라우팅이 가능하다. 라우터는 네트워크 부분만 보고 방향을 결정한다.

---

## IPv4 주소 구조

IPv4 주소는 **32비트**로, 점으로 구분된 4개의 10진수로 표기한다. 각 옥텟(octet)은 8비트이므로 0~255 범위다.

```
192.168.1.100

11000000.10101000.00000001.01100100
   192      168       1       100
```

IP 주소는 **네트워크 부분 + 호스트 부분**으로 구성된다.

- 네트워크 부분: 어느 네트워크에 속하는지 (도로명)
- 호스트 부분: 그 네트워크 내 어떤 장치인지 (건물 번호)

같은 네트워크에 있는 장치들은 네트워크 부분이 동일하다. 라우터는 네트워크 부분만 보고 패킷을 어느 방향으로 보낼지 결정한다.

## Classful Addressing (역사적 배경)

초기 인터넷은 IP 주소를 **클래스(Class)**로 나눴다. 첫 번째 옥텟의 범위로 클래스가 결정되고, 클래스에 따라 네트워크/호스트 비트가 고정되었다.

| 클래스 | 첫 옥텟 | 네트워크 비트 | 호스트 비트 | 네트워크 수 | 호스트 수/네트워크 |
|--------|---------|--------------|------------|------------|------------------|
| A | 1-126 | 8 | 24 | 126 | 약 1677만 |
| B | 128-191 | 16 | 16 | 16,384 | 65,534 |
| C | 192-223 | 24 | 8 | 약 209만 | 254 |
| D | 224-239 | - | - | 멀티캐스트용 | - |
| E | 240-255 | - | - | 예약/실험용 | - |

127.x.x.x는 루프백(loopback)으로 예약되어 클래스에 포함되지 않는다.

### Classful의 문제점

클래스 기반 할당은 **극심한 낭비**를 초래했다.

- 중소기업이 500개 호스트 필요 → Class C(254개)로는 부족, Class B(65,534개) 할당 → 65,000개 낭비
- Class A는 대기업에만 할당, 대부분의 주소 미사용
- Class C는 너무 작아서 여러 개 할당 필요 → 라우팅 테이블 비대화

이 문제를 해결하기 위해 **CIDR(Classless Inter-Domain Routing)**이 등장했다.

## CIDR와 서브넷 마스크

### CIDR 표기법

CIDR은 클래스 개념을 버리고, **네트워크 비트 수를 자유롭게 지정**한다. 슬래시 뒤에 네트워크 비트 수를 붙인다.

```
192.168.1.0/24  → 네트워크 24비트, 호스트 8비트
10.0.0.0/8      → 네트워크 8비트, 호스트 24비트
172.16.0.0/20   → 네트워크 20비트, 호스트 12비트
```

/24가 아니라 /20, /22, /27 등 필요한 만큼만 할당할 수 있어 낭비가 줄어든다.

### 서브넷 마스크

네트워크와 호스트를 구분하는 기준이 **서브넷 마스크**다. 연속된 1이 네트워크 부분, 연속된 0이 호스트 부분이다.

```
/24 = 255.255.255.0   = 11111111.11111111.11111111.00000000
/16 = 255.255.0.0     = 11111111.11111111.00000000.00000000
/20 = 255.255.240.0   = 11111111.11111111.11110000.00000000
/27 = 255.255.255.224 = 11111111.11111111.11111111.11100000
```

IP 주소와 서브넷 마스크를 **AND 연산**하면 네트워크 주소가 나온다.

```
IP:        192.168.1.100  = 11000000.10101000.00000001.01100100
Mask /24:  255.255.255.0  = 11111111.11111111.11111111.00000000
           ─────────────────────────────────────────────────────
Network:   192.168.1.0    = 11000000.10101000.00000001.00000000
```

### 주요 계산

서브넷에서:

- 호스트 비트 수 = 32 - n
- 총 IP 수 = 2^(32-n)
- 사용 가능 호스트 수 = 2^(32-n) - 2 (네트워크 주소와 브로드캐스트 제외)
- 브로드캐스트 = 호스트 비트가 모두 1

| CIDR | 서브넷 마스크 | 호스트 수 |
|------|--------------|----------|
| /24 | 255.255.255.0 | 254 |
| /25 | 255.255.255.128 | 126 |
| /26 | 255.255.255.192 | 62 |
| /27 | 255.255.255.224 | 30 |
| /28 | 255.255.255.240 | 14 |
| /29 | 255.255.255.248 | 6 |
| /30 | 255.255.255.252 | 2 |

/30은 2개 호스트만 가능해서 **point-to-point 링크**(라우터 간 연결)에 사용된다.

## 서브넷팅 실전

### 왜 서브넷팅이 필요한가?

회사에 192.168.1.0/24가 할당되었다. 254개 호스트를 수용할 수 있다. 하지만 개발팀, 마케팅팀, 인사팀을 분리해야 한다면?

- 같은 네트워크에 두면: 브로드캐스트가 전체로 퍼짐, 보안 분리 불가
- 부서별로 서브넷 분리 필요

서브넷팅은 호스트 비트 일부를 네트워크 비트로 전환하여 하나의 네트워크를 여러 개로 나누는 것이다.

### 예시 1: 4개 부서로 분리

192.168.1.0/24를 4개 서브넷으로 나누려면, 2비트가 필요하다 (2^2 = 4).

```
원본: /24 (호스트 8비트)
변경: /26 (호스트 6비트, 서브넷 2비트)

호스트 비트 8개 중 2개를 서브넷 비트로:
xx000000 → 4가지 조합 (00, 01, 10, 11)
```

| 서브넷 | 네트워크 주소 | 호스트 범위 | 브로드캐스트 |
|--------|-------------|------------|-------------|
| 1 | 192.168.1.0/26 | .1 ~ .62 | .63 |
| 2 | 192.168.1.64/26 | .65 ~ .126 | .127 |
| 3 | 192.168.1.128/26 | .129 ~ .190 | .191 |
| 4 | 192.168.1.192/26 | .193 ~ .254 | .255 |

각 서브넷은 62개 호스트를 수용한다.

### 예시 2: 다양한 크기의 서브넷 (VLSM)

실제로는 부서마다 필요한 호스트 수가 다르다. **VLSM(Variable Length Subnet Mask)**을 사용하면 서브넷마다 다른 크기를 할당할 수 있다.

요구사항:
- 개발팀: 100명
- 마케팅팀: 50명  
- 인사팀: 20명
- 서버실: 10명

큰 서브넷부터 할당한다:

```
개발팀 (100명): /25 필요 (126개 호스트)
  → 192.168.1.0/25 (.1 ~ .126)

마케팅팀 (50명): /26 필요 (62개 호스트)
  → 192.168.1.128/26 (.129 ~ .190)

인사팀 (20명): /27 필요 (30개 호스트)
  → 192.168.1.192/27 (.193 ~ .222)

서버실 (10명): /28 필요 (14개 호스트)
  → 192.168.1.224/28 (.225 ~ .238)

남은 공간: 192.168.1.240/28 (여유분)
```

### 서브넷 계산 빠른 방법

/26의 네트워크 주소들을 계산하려면:

1. 호스트 비트 = 32 - 26 = 6
2. 블록 크기 = 2^6 = 64
3. 네트워크 주소 = 0, 64, 128, 192 (64씩 증가)

주어진 IP가 어느 서브넷에 속하는지 알려면:

```
192.168.1.150은 /26에서 어느 서브넷?

블록 크기 = 64
150 ÷ 64 = 2.xxx
2 × 64 = 128

→ 192.168.1.128/26 서브넷에 속함
```

## 사설 IP와 공인 IP

### IP 주소 부족 문제

IPv4는 32비트라 약 43억 개다. 전 세계 인구 80억에, 한 사람이 여러 기기를 사용하니 턱없이 부족하다.

### 사설 IP (Private IP)

**RFC 1918**에서 정의한 다음 대역은 인터넷에서 라우팅되지 않는다. 내부 네트워크에서 자유롭게 중복 사용할 수 있다.

| 대역 | CIDR | 범위 | 호스트 수 | 용도 |
|------|------|------|----------|------|
| Class A | 10.0.0.0/8 | 10.0.0.0 ~ 10.255.255.255 | 약 1677만 | 대기업, 클라우드, VPN |
| Class B | 172.16.0.0/12 | 172.16.0.0 ~ 172.31.255.255 | 약 104만 | 중규모 기업 |
| Class C | 192.168.0.0/16 | 192.168.0.0 ~ 192.168.255.255 | 약 6.5만 | 가정, 소규모 사무실 |

가정집 공유기의 192.168.0.x와 옆집의 192.168.0.x는 충돌하지 않는다. 각자의 내부 네트워크이고, 인터넷으로 나갈 때 NAT로 공인 IP로 변환되기 때문이다.

### 공인 IP (Public IP)

인터넷에서 라우팅 가능한 IP다. 전 세계적으로 유일해야 하므로 IANA → RIR → ISP → 사용자 순으로 계층적 할당된다.

### 특수 목적 IP

| 주소/대역 | 용도 | 설명 |
|----------|------|------|
| 127.0.0.0/8 | 루프백 | 자기 자신. 127.0.0.1이 localhost |
| 0.0.0.0 | 모든 IP / 기본 라우트 | 서버 바인딩 시 모든 인터페이스 |
| 255.255.255.255 | 제한된 브로드캐스트 | 같은 네트워크 전체 |
| 169.254.0.0/16 | Link-local (APIPA) | DHCP 실패 시 자동 할당 |
| 224.0.0.0/4 | 멀티캐스트 | 그룹 통신용 (Class D) |

169.254.x.x가 보이면 DHCP 서버에 문제가 있다는 신호다.

## MAC 주소와 IP 주소의 관계

### 왜 둘 다 필요한가?

- **MAC 주소**: L2, 같은 네트워크 내 인접 장치 식별. 하드웨어에 고정.
- **IP 주소**: L3, 네트워크 간 라우팅. 논리적 할당, 변경 가능.

### 라우터 통과 시 변화

패킷이 라우터를 지날 때 **IP는 유지**, **MAC은 변경**된다.

```
[PC] ──── [Router A] ──── [Router B] ──── [Server]
192.168.1.100           10.0.0.1              10.0.0.50
MAC: AA                 MAC: BB, CC           MAC: DD

구간 1: PC → Router A
┌─────────────────────────────────────┐
│ Src MAC: AA    │ Dst MAC: BB       │ ← L2 헤더
├─────────────────────────────────────┤
│ Src IP: 192.168.1.100              │
│ Dst IP: 10.0.0.50                  │ ← L3 헤더 (불변)
└─────────────────────────────────────┘

구간 2: Router A → Router B
┌─────────────────────────────────────┐
│ Src MAC: CC    │ Dst MAC: ??       │ ← MAC 변경됨
├─────────────────────────────────────┤
│ Src IP: 192.168.1.100              │
│ Dst IP: 10.0.0.50                  │ ← IP 유지
└─────────────────────────────────────┘

구간 3: Router B → Server
┌─────────────────────────────────────┐
│ Src MAC: ??    │ Dst MAC: DD       │ ← MAC 또 변경
├─────────────────────────────────────┤
│ Src IP: 192.168.1.100              │
│ Dst IP: 10.0.0.50                  │ ← IP 유지
└─────────────────────────────────────┘
```

MAC은 "바로 다음 장치"를, IP는 "최종 목적지"를 가리킨다.

## ARP (Address Resolution Protocol)

### 왜 ARP가 필요한가?

IP 패킷을 전송하려면 이더넷 프레임으로 감싸야 한다. 프레임에는 목적지 MAC 주소가 필요하다. 하지만 애플리케이션은 IP 주소만 안다. **ARP**는 "이 IP의 MAC이 뭐야?"라는 질문에 답한다.

### ARP 패킷 구조

```
┌────────────────────────────────────────────────────────┐
│ Hardware Type (2B) │ Protocol Type (2B)               │
├────────────────────┼──────────────────────────────────┤
│ HW Addr Len (1B)   │ Proto Addr Len (1B) │ Opcode (2B)│
├────────────────────┴──────────────────────────────────┤
│ Sender Hardware Address (MAC) - 6 bytes               │
├───────────────────────────────────────────────────────┤
│ Sender Protocol Address (IP) - 4 bytes                │
├───────────────────────────────────────────────────────┤
│ Target Hardware Address (MAC) - 6 bytes               │
├───────────────────────────────────────────────────────┤
│ Target Protocol Address (IP) - 4 bytes                │
└───────────────────────────────────────────────────────┘
```

- Hardware Type: 1 = Ethernet
- Protocol Type: 0x0800 = IPv4
- Opcode: 1 = Request, 2 = Reply

### ARP 동작 과정

192.168.1.100(MAC: AA:AA:AA:AA:AA:AA)이 192.168.1.20에게 패킷을 보내려 한다.

**Step 1: ARP 캐시 확인**

```bash
$ arp -a
# 192.168.1.20이 없으면 ARP Request 필요
```

**Step 2: ARP Request (브로드캐스트)**

```
Ethernet Header:
  Src MAC: AA:AA:AA:AA:AA:AA
  Dst MAC: FF:FF:FF:FF:FF:FF (브로드캐스트)
  
ARP Payload:
  Opcode: 1 (Request)
  Sender MAC: AA:AA:AA:AA:AA:AA
  Sender IP: 192.168.1.100
  Target MAC: 00:00:00:00:00:00 (모름)
  Target IP: 192.168.1.20
```

같은 네트워크의 모든 장치가 이 요청을 받지만, 192.168.1.20만 응답한다.

**Step 3: ARP Reply (유니캐스트)**

```
Ethernet Header:
  Src MAC: BB:BB:BB:BB:BB:BB
  Dst MAC: AA:AA:AA:AA:AA:AA (요청자에게 직접)
  
ARP Payload:
  Opcode: 2 (Reply)
  Sender MAC: BB:BB:BB:BB:BB:BB
  Sender IP: 192.168.1.20
  Target MAC: AA:AA:AA:AA:AA:AA
  Target IP: 192.168.1.100
```

**Step 4: ARP 캐시 저장**

```
192.168.1.20 → BB:BB:BB:BB:BB:BB (TTL: 20분)
```

### 다른 네트워크로 보낼 때

목적지가 다른 네트워크(예: 10.0.0.50)면 어떻게 될까?

- 10.0.0.50은 같은 서브넷이 아님
- ARP Request를 보내도 응답 없음
- 대신 **기본 게이트웨이(라우터)**의 MAC을 ARP로 얻음
- 프레임: Dst MAC = 라우터, IP Dst = 10.0.0.50
- 라우터가 받아서 다음 홉으로 전달

### Gratuitous ARP

자기 자신의 IP로 ARP Request를 보내는 것이다. "내 IP의 MAC이 뭐야?"라고 자기 자신에게 묻는 셈이다.

용도:
- IP 충돌 감지: 응답이 오면 다른 장치가 같은 IP 사용 중
- ARP 캐시 갱신: IP나 MAC이 바뀌었을 때 네트워크에 알림
- Failover: VRRP/HSRP에서 Active 라우터 변경 시

### Proxy ARP

라우터가 다른 네트워크에 있는 호스트를 대신하여 ARP에 응답하는 것이다.

- 호스트 A가 다른 서브넷의 B에게 ARP Request
- 원래는 응답 없어야 함
- 라우터가 "내가 대신 전달해줄게" 하며 자신의 MAC으로 응답
- A는 라우터 MAC으로 프레임 전송, 라우터가 B로 전달

서브넷 설정 없이 통신 가능하지만, 보안/관리 문제로 현대에는 권장하지 않는다.

### ARP Spoofing (보안)

ARP는 인증이 없다. 공격자가 거짓 ARP Reply를 보내 ARP 캐시를 오염시킬 수 있다.

```
공격자: "192.168.1.1(게이트웨이)의 MAC은 [공격자 MAC]이야"
피해자: ARP 캐시 갱신
피해자 → 게이트웨이 트래픽이 모두 공격자에게로
```

MITM(Man-in-the-Middle) 공격의 기초다. 방어:

- Dynamic ARP Inspection (스위치 기능)

## NAT (Network Address Translation)

### 왜 NAT가 필요한가?

사설 IP는 인터넷에서 라우팅되지 않는다. 192.168.1.100에서 google.com으로 요청을 보내면, Google은 응답을 192.168.1.100으로 보내야 하는데, 인터넷 라우터는 192.168.1.100이 어디 있는지 모른다.

**NAT**는 사설 IP ↔ 공인 IP 변환으로 이 문제를 해결한다.

### NAT 유형

**Static NAT**: 사설 IP와 공인 IP가 1:1 매핑. 외부에서 내부 서버 접근 시 사용.

```
192.168.1.10 ↔ 1.2.3.10 (항상 고정)
192.168.1.20 ↔ 1.2.3.20 (항상 고정)
```

**Dynamic NAT**: 사설 IP가 공인 IP 풀에서 동적 할당. 사용 후 반환.

```
192.168.1.10 → 1.2.3.10 (지금 사용 중)
192.168.1.20 → 1.2.3.11 (지금 사용 중)
192.168.1.30 → 풀 소진 시 대기
```

**PAT (Port Address Translation)**: NAPT, Masquerading이라고도 함. 포트 번호로 구분하여 **하나의 공인 IP로 수천 개 내부 장치** 지원. 가정용 공유기가 사용하는 방식.

### PAT 동작 상세

```
내부:
  PC1: 192.168.1.100
  PC2: 192.168.1.101
공유기:
  내부: 192.168.1.1
  외부: 1.2.3.4 (공인 IP)
```

**Outbound (내부 → 외부)**

```
PC1이 google.com:443 접속:
원본: 192.168.1.100:50000 → 142.250.196.110:443

공유기 NAT 변환:
1.2.3.4:30001 → 142.250.196.110:443

NAT 테이블 기록:
┌─────────────────────┬──────────────────┬─────────────────┐
│ Internal           │ External         │ Destination     │
├─────────────────────┼──────────────────┼─────────────────┤
│ 192.168.1.100:50000│ 1.2.3.4:30001   │ 142.250...:443  │
└─────────────────────┴──────────────────┴─────────────────┘
```

**Inbound (외부 → 내부)**

```
Google 응답:
142.250.196.110:443 → 1.2.3.4:30001

NAT 테이블 참조 → 역변환:
142.250.196.110:443 → 192.168.1.100:50000

PC1에게 전달
```

**여러 내부 장치:**

```
NAT 테이블:
┌─────────────────────┬──────────────────┐
│ Internal           │ External         │
├─────────────────────┼──────────────────┤
│ 192.168.1.100:50000│ 1.2.3.4:30001   │
│ 192.168.1.100:50001│ 1.2.3.4:30002   │
│ 192.168.1.101:50000│ 1.2.3.4:30003   │
│ 192.168.1.102:60000│ 1.2.3.4:30004   │
└─────────────────────┴──────────────────┘
```

외부 포트(30001, 30002...)로 구분하므로 하나의 공인 IP로 수만 개 연결 가능.

### 포트 포워딩 (DNAT)

외부에서 내부 서버에 접근하려면 **포트 포워딩**이 필요하다.

```
설정: 1.2.3.4:80 → 192.168.1.50:80

외부 사용자가 1.2.3.4:80 접속
공유기가 192.168.1.50:80으로 전달
```

### NAT의 문제점

**End-to-End 연결 방해**: P2P, VoIP, 온라인 게임에서 양쪽이 모두 NAT 뒤에 있으면 직접 연결이 어렵다.

- STUN: NAT 유형 파악, 외부에서 보이는 IP:Port 확인
- TURN: 릴레이 서버를 통한 중계
- ICE: STUN + TURN 조합으로 최적 경로 탐색
- NAT Traversal, Hole Punching 기법 필요

**일부 프로토콜 호환 문제**: FTP, SIP 등은 페이로드 안에 IP 주소를 포함한다. NAT가 헤더만 변환하면 페이로드의 IP는 여전히 사설 IP라서 문제가 생긴다. ALG(Application Layer Gateway)가 필요하다.

**성능 오버헤드**: 모든 패킷마다 IP/Port 변환 및 테이블 조회.

## 면접 예상 질문

**Q. IP 주소와 MAC 주소의 차이점은?**

MAC 주소는 L2 주소로 48비트, NIC에 하드웨어적으로 할당되며 같은 네트워크 내 통신에 사용된다. 평면적이라 라우팅이 불가능하다. IP 주소는 L3 주소로 32비트(IPv4), 논리적으로 할당되며 네트워크+호스트 계층 구조로 라우팅이 가능하다. 패킷이 라우터를 통과할 때 MAC은 매 홉마다 바뀌고 IP는 유지된다.

**Q. 서브넷 마스크의 역할은?**

IP 주소에서 네트워크 부분과 호스트 부분을 구분하는 기준이다. 서브넷 마스크의 1인 비트는 네트워크, 0인 비트는 호스트를 나타낸다. IP 주소와 서브넷 마스크를 AND 연산하면 네트워크 주소가 나온다. CIDR 표기법(/24 등)은 네트워크 비트 수를 나타낸다.

**Q. 192.168.1.130/26의 네트워크 주소, 브로드캐스트, 호스트 범위는?**

/26은 호스트 비트가 6개이므로 블록 크기는 64다. 130 ÷ 64 = 2.xx이므로 2 × 64 = 128. 네트워크 주소는 192.168.1.128, 브로드캐스트는 192.168.1.191(128+63), 호스트 범위는 .129 ~ .190으로 62개다.

**Q. ARP란 무엇인가?**

IP 주소로 MAC 주소를 알아내는 프로토콜이다. 브로드캐스트로 "이 IP의 MAC이 뭐야?" ARP Request를 보내면 해당 호스트가 유니캐스트로 자신의 MAC을 Reply한다. 결과는 ARP 캐시에 저장하여 재사용한다. ARP는 인증이 없어서 ARP Spoofing 공격에 취약하다.

**Q. NAT란 무엇이고 왜 필요한가?**

Network Address Translation으로, 사설 IP와 공인 IP를 변환한다. IPv4 주소 부족 문제를 해결하기 위해 내부에서는 사설 IP를 사용하고, 인터넷으로 나갈 때 공인 IP로 변환한다. PAT는 포트 번호까지 활용하여 하나의 공인 IP로 수천 개 내부 장치를 지원한다. 단점으로는 P2P 연결 방해, 일부 프로토콜 호환 문제가 있다.

**Q. 사설 IP 대역을 말해보시오.**

RFC 1918에서 정의한 세 대역이 있다. 10.0.0.0/8은 약 1677만 개로 대기업/클라우드에서 사용한다. 172.16.0.0/12는 약 104만 개로 중규모 네트워크에 사용한다. 192.168.0.0/16은 약 6.5만 개로 가정/소규모 사무실에서 사용한다.
