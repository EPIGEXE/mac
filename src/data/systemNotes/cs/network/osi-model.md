# OSI 7계층

## 왜 계층화가 필요한가?

네트워크 통신의 본질은 **"멀리 떨어진 두 프로세스가 데이터를 주고받는 것"**이다. 단순해 보이지만, 이를 위해서는 다음과 같은 과정이 수반된다.

- 비트를 전기/광/무선 신호로 변환 (Physical Layer)
- 인접 장치 간 프레임 전달, 오류 검출, 충돌 방지 (Data Link Layer)
- 수십억 장치 중 목적지를 찾아 라우팅 (Network Layer)
- 신뢰성 있는 전송, 순서 보장, 흐름/혼잡 제어 (Transport Layer)
- 세션 관리, 데이터 표현, 애플리케이션 로직 (Session/Presentation/Application)

이를 하나의 모놀리식 시스템으로 구현하면 물리 매체 변경 시 전체 재설계, 문제 발생 시 원인 파악 불가, 애플리케이션마다 네트워크 스택 재구현 등의 재앙이 발생한다.

계층화는 **관심사 분리(Separation of Concerns)**를 네트워크에 적용한 것이다.

- **단일** 책임: 각 계층은 하나의 명확한 기능만 담당
- **추상화**: 각 계층은 하위 계층의 복잡성을 완전히 숨김
- **느슨한** 결합: 한 계층 변경이 다른 계층에 영향 없음

이 원리 덕분에 물리 매체가 동축 케이블에서 광섬유, Wi-Fi로 바뀌어도 Application 코드는 수정이 불필요하다.

## OSI vs TCP/IP

OSI는 1984년 ISO가 발표한 **이론적 참조 모델(7계층)**이고, TCP/IP는 1970년대 ARPANET에서 시작된 **실제 구현(4계층)**이다.

```
     OSI 7 Layer              TCP/IP 4 Layer           실제 프로토콜
┌─────────────────┐        ┌─────────────────┐
│   Application   │        │                 │        HTTP, FTP, SMTP,
├─────────────────┤        │   Application   │        DNS, SSH, DHCP
│  Presentation   │───────→│                 │
├─────────────────┤        │                 │
│    Session      │        └─────────────────┘
├─────────────────┤        ┌─────────────────┐
│   Transport     │───────→│   Transport     │        TCP, UDP
├─────────────────┤        └─────────────────┘
│    Network      │───────→│    Internet     │        IP, ICMP, ARP
├─────────────────┤        └─────────────────┘
│   Data Link     │        ┌─────────────────┐
├─────────────────┤───────→│  Network Access │        Ethernet, Wi-Fi
│    Physical     │        └─────────────────┘
└─────────────────┘
```

OSI가 발표되었을 때 TCP/IP는 이미 수년간 검증을 마쳤고, BSD Unix에 무료로 포함되어 사실상 표준이었다. 실제 인터넷은 TCP/IP를 사용하지만, OSI는 "이 문제가 L2인가 L3인가?"라는 계층별 분석 프레임워크와 "L7 로드밸런서" 같은 공통 언어를 제공한다.

## L1: Physical Layer

컴퓨터는 0과 1의 디지털 데이터를 다루지만, 이 데이터를 다른 컴퓨터로 보내려면 물리적 신호로 변환해야 한다. Physical Layer가 이 변환을 담당하며, 다음 문제들을 해결한다.

- 비트 표현: 0과 1을 어떤 전압/빛/주파수로 나타낼 것인가
- 동기화: 비트의 시작과 끝을 어떻게 구분할 것인가
- 감쇠 복구: 거리가 멀어져 약해진 신호를 어떻게 복원할 것인가

### 전송 매체

신호가 실제로 이동하는 물리적 경로다.

- UTP(랜선): 가장 보편적, 저렴, 신호 감쇠로 100m 제한
- 광섬유: 빛 사용, EMI 면역, 수십km 전송 가능, 고비용
- Wi-Fi: 무선 이동성, 공유 매체라 혼잡 시 대역폭 분할

### 장비

**리피터**는 거리가 멀어져 감쇠된 신호를 증폭하여 전송 거리를 연장하는 장비다. **허브**는 여러 포트를 가진 리피터로, 한 포트에서 받은 신호를 다른 모든 포트로 복제한다.

- 리피터: 신호 증폭, 전송 거리 연장
- 허브: 멀티포트 리피터, 모든 포트로 신호 복제

허브는 목적지를 구분하지 못하고 무조건 모든 포트로 보내므로 비효율적이다. 또한 여러 장치가 동시에 전송하면 신호가 충돌한다. 현대 네트워크에서는 스위치로 대체되어 거의 사용하지 않는다.

## L2: Data Link Layer

Physical Layer는 비트를 신호로 변환해서 전송하지만, 두 가지를 모른다.

- 누구에게 보내는지 모름: 허브는 모든 포트로 복제할 뿐
- 데이터의 경계를 모름: 비트 스트림이 끝없이 흐를 뿐

Data Link Layer는 **MAC 주소**로 장치를 식별하고, **프레임**으로 데이터 경계를 정의하여 이 문제를 해결한다.

### MAC 주소

모든 네트워크 카드(NIC)에는 제조 시 **MAC 주소**가 하드웨어에 새겨진다. 48비트(6바이트)로, `AA:BB:CC:DD:EE:FF` 형태로 표기한다.

- 상위 24비트(OUI): IEEE가 제조사에 할당 (예: Apple, Intel)
- 하위 24비트: 제조사가 각 NIC에 부여한 일련번호
- FF:FF:FF:FF:FF:FF: 브로드캐스트, 같은 네트워크의 모든 장치가 수신

### 프레임

비트 스트림에서 데이터 단위를 구분하는 구조다. 이더넷 프레임은 다음과 같다.

```
┌──────────┬──────────┬──────────┬────────────────┬──────┐
│ Dst MAC  │ Src MAC  │EtherType │    Payload     │ FCS  │
│  6 B     │  6 B     │  2 B     │   46-1500 B    │ 4 B  │
└──────────┴──────────┴──────────┴────────────────┴──────┘
```

- Dst MAC: 목적지 MAC 주소
- Src MAC: 출발지 MAC 주소
- EtherType: 상위 프로토콜 식별 (0x0800=IPv4, 0x0806=ARP)
- Payload: 실제 데이터, 46~1500바이트 (MTU)
- FCS: CRC-32 체크섬으로 오류 검출

### 오류 검출

전송 중 전자기 간섭 등으로 비트가 뒤집힐 수 있다. **FCS**는 프레임 전체를 CRC-32로 계산한 체크섬이다. 수신자가 같은 계산을 해서 비교하고, 다르면 오류가 발생한 것이다.

- 오류 검출만 함, 정정은 안 함
- 오류 발견 시 프레임을 조용히 폐기
- 재전송 요청 안 함, 재전송은 상위 계층(TCP)의 몫

### 충돌과 CSMA/CD

여러 장치가 같은 매체를 공유하면 동시 전송 시 신호가 겹쳐 충돌이 발생한다. **CSMA/CD**는 유선 이더넷에서 이를 처리하는 방식이다.

- Carrier Sense: 전송 전에 회선이 비어 있는지 확인
- Multiple Access: 여러 장치가 같은 매체 공유
- Collision Detection: 충돌 감지 시 전송 중단, 랜덤 시간 후 재시도

현대 스위치 기반 네트워크에서는 각 포트가 별도의 충돌 도메인이고 전이중 통신을 지원하므로 충돌이 사실상 발생하지 않는다.

### 장비: 스위치

**스위치**는 허브와 달리 MAC 주소를 이해하는 L2 장비다. **MAC 주소 테이블**을 유지하며 학습한다.

- 학습: 프레임 수신 시 출발지 MAC과 포트를 테이블에 기록
- Forwarding: 목적지 MAC이 테이블에 있으면 해당 포트로만 전송
- Flooding: 목적지 MAC이 테이블에 없으면 모든 포트로 전송

허브는 모든 포트로 무조건 복제하지만, 스위치는 필요한 포트로만 전송하여 효율적이다.

## L3: Network Layer

Data Link Layer는 MAC 주소로 같은 네트워크 내 장치끼리 통신하게 해준다. 하지만 MAC 주소는 **평면적(flat)**이라서 한계가 있다.

- AA:BB:CC:DD:EE:FF를 보고 "이 장치가 어느 네트워크에 있는지" 알 수 없음
- 전 세계 수십억 MAC 주소의 경로를 기억하는 것은 불가능
- 다른 네트워크로 라우팅할 방법이 없음

Network Layer는 **계층적 주소 체계(IP 주소)**로 이 문제를 해결한다.

### IP 주소

**IP 주소(IPv4)**는 32비트로, `192.168.1.100`처럼 점으로 구분된 4개의 10진수로 표기한다. 핵심은 **네트워크 부분 + 호스트 부분**으로 나뉜다는 것이다.

- 네트워크 부분: 어느 네트워크인지 (서울시 강남구)
- 호스트 부분: 그 네트워크 내 어떤 장치인지 (123번지)
- 서브넷 마스크: 네트워크/호스트 구분 기준 (255.255.255.0 = /24)

192.168.1.100/24의 경우, 앞 24비트(192.168.1)가 네트워크, 뒤 8비트(100)가 호스트다.

### 사설 IP와 공인 IP

IPv4는 32비트라 약 43억 개뿐이다. 모든 장치에 부여하기엔 부족해서 **사설 IP**가 등장했다. 다음 대역은 인터넷에서 라우팅되지 않고, 내부 네트워크에서 자유롭게 중복 사용할 수 있다.

- 10.0.0.0/8: 대기업, 클라우드
- 172.16.0.0/12: 중규모 네트워크
- 192.168.0.0/16: 가정용 공유기에서 흔히 사용

특수 목적 IP도 있다.

- 127.0.0.1: 루프백, 자기 자신 (localhost)
- 0.0.0.0: 모든 인터페이스 (서버 바인딩 시)
- 255.255.255.255: 브로드캐스트

### 라우팅

같은 네트워크 내에서는 MAC 주소로 직접 통신한다. 다른 네트워크와 통신하려면 **라우팅**이 필요하다.

**라우터**는 서로 다른 네트워크를 연결하는 L3 장비다. **라우팅 테이블**을 참조하여 "이 목적지 IP는 어느 방향(다음 홉)으로 보내야 하는지" 결정한다.

- 같은 네트워크: 직접 전송
- 다른 네트워크: 게이트웨이(라우터)로 전송
- 라우터가 다시 라우팅 테이블 참조 → 목적지 도달까지 반복

### ARP

IP 주소로 목적지를 알았지만, 실제 전송은 L2(이더넷)로 해야 한다. 프레임에는 MAC 주소가 필요한데, IP만 알고 MAC은 모른다. **ARP(Address Resolution Protocol)**가 이를 해결한다.

- A가 192.168.1.20과 통신하려 함
- ARP 캐시에 해당 MAC이 없음
- "192.168.1.20의 MAC이 뭐야?" 브로드캐스트로 ARP Request
- 해당 IP를 가진 B가 "내 MAC은 BB:BB:BB:BB:BB:BB야" 유니캐스트로 Reply
- A가 ARP 캐시에 저장 (보통 20분 유지)

### NAT

사설 IP는 인터넷에서 라우팅되지 않는다. 192.168.1.100에서 google.com으로 패킷을 보내도, 인터넷 라우터는 응답을 돌려보낼 수 없다.

**NAT(Network Address Translation)**가 이를 해결한다. 공유기가 내부 사설 IP를 자신의 공인 IP로 변환해서 내보내고, 응답이 오면 다시 원래 사설 IP로 변환해서 전달한다.

- 사설 IP → 공인 IP 변환하여 전송
- 응답 수신 시 공인 IP → 사설 IP 역변환
- PAT: 포트 번호까지 활용하여 하나의 공인 IP로 수천 개 내부 장치 지원

## L4: Transport Layer

Network Layer는 패킷을 **호스트까지** 배달한다. 하지만 호스트에는 여러 프로세스가 동시에 실행된다.

- 웹 브라우저, 카카오톡, 게임이 동시에 네트워크 사용
- 도착한 패킷이 어떤 프로세스로 가야 하는지 알 수 없음

또한 IP는 **"최선형(Best-effort)"** 프로토콜이다.

- 패킷이 도착할지 보장 안 함
- 순서대로 올지 보장 안 함
- 중복되지 않을지 보장 안 함

Transport Layer는 **포트 번호**로 프로세스를 구분하고, **TCP/UDP**로 전송 품질을 제어한다.

### 포트 번호

IP 주소가 건물 주소라면, 포트 번호는 호수다. 16비트(0~65535)로 표현한다.

- 0~1023 (Well-known): HTTP 80, HTTPS 443, SSH 22, DNS 53
- 1024~49151 (Registered): MySQL 3306, PostgreSQL 5432, Redis 6379
- 49152~65535 (Dynamic): 클라이언트가 임시로 사용

### TCP

**TCP**는 IP 위에서 신뢰성을 제공한다.

- 연결 지향: 3-way handshake로 연결 수립 후 데이터 전송
- 순서 보장: 각 바이트에 Sequence Number 부여
- 손실 복구: ACK가 안 오면 재전송
- 흐름 제어: 수신자가 처리할 수 있는 속도로 전송
- 혼잡 제어: 네트워크가 막히면 전송량 줄임

HTTP, 파일 전송, 이메일 등 데이터가 정확히 도착해야 하는 경우 사용한다.

### UDP

**UDP**는 신뢰성 기능이 없다. 연결 없이 바로 보내고, 도착 여부를 확인하지 않는다. 헤더가 8바이트로 TCP(20~60바이트)보다 가볍다.

- DNS: 작은 요청/응답, 실패 시 재시도하면 됨
- 실시간 스트리밍: 1초 전 프레임이 늦게 와봤자 소용없음
- 온라인 게임: 지연이 손실보다 치명적

| 구분 | TCP | UDP |
|------|-----|-----|
| 연결 | 연결 지향 | 비연결 |
| 신뢰성 | 보장 | 미보장 |
| 순서 | 보장 | 미보장 |
| 속도 | 상대적 느림 | 빠름 |
| 용도 | HTTP, 파일, 이메일 | DNS, 스트리밍, 게임 |

### 소켓

**소켓**은 네트워크 통신의 엔드포인트다. TCP 연결은 4가지 조합으로 유일하게 식별된다.

- 출발지 IP
- 출발지 Port
- 목적지 IP
- 목적지 Port

그래서 웹 서버가 80번 포트 하나로 수만 개 동시 연결을 처리할 수 있다. 서버 포트(80)는 같아도 각 클라이언트의 IP와 Port가 다르므로 서로 다른 연결이다.

## L5~L7: Session, Presentation, Application

TCP/IP 모델에서는 이 세 계층이 **Application Layer 하나로 통합**된다. 실제로 현대 애플리케이션에서 이 경계는 모호하다.

### Session Layer

세션의 수립, 유지, 종료를 관리한다.

- HTTP: Stateless라서 쿠키/세션으로 상태 유지
- WebSocket: TCP 연결을 유지하며 양방향 통신
- TLS: Session Resumption으로 재협상 생략

### Presentation Layer

데이터 형식 변환, 인코딩, 암호화를 담당한다.

- 문자 인코딩: UTF-8, ASCII
- 직렬화: JSON, XML, Protocol Buffers
- 암호화: TLS
- 압축: gzip, Brotli

### Application Layer

사용자와 직접 상호작용하는 애플리케이션 프로토콜이다.

| 프로토콜 | 포트 | 전송 | 용도 |
|---------|------|------|------|
| HTTP | 80 | TCP | 웹 |
| HTTPS | 443 | TCP | 웹 (암호화) |
| DNS | 53 | UDP/TCP | 도메인 → IP |
| SSH | 22 | TCP | 원격 접속 |

이 프로토콜들은 이후 문서에서 상세히 다룬다.

## 캡슐화와 역캡슐화

데이터가 송신 측에서 계층을 내려갈 때, 각 계층은 자신의 헤더를 추가한다. 이를 **캡슐화(Encapsulation)**라 한다.

```
Application:  [        HTTP Request Data        ]
                          ↓
Transport:    [ TCP Header |    HTTP Data       ]  ← Segment
                          ↓  
Network:      [ IP Header | TCP | HTTP Data     ]  ← Packet
                          ↓
Data Link:    [ Eth Header | IP | TCP | Data | FCS ]  ← Frame
                          ↓
Physical:     101101010010101010110...              ← Bits
```

핵심은 **투명성**이다. 각 계층은 상위 계층의 데이터를 불투명한 페이로드로 취급한다.

- TCP는 페이로드가 HTTP인지 FTP인지 모름
- IP는 TCP인지 UDP인지만 Protocol 필드로 알 뿐
- Ethernet은 IP인지 ARP인지만 EtherType으로 알 뿐

수신 측에서는 반대로 각 계층이 자신의 헤더를 확인하고 제거하며 올라간다.

패킷이 라우터를 통과할 때:

- MAC 주소: 매 홉마다 변경 (라우터가 새로 생성)
- IP 주소: 유지 (NAT 없으면)
- Port: 유지

이것이 L2 주소(MAC)와 L3 주소(IP)의 근본적 차이다. MAC은 "다음 장치"를, IP는 "최종 목적지"를 가리킨다.

## 면접 예상 질문

**Q. OSI 7계층을 설명하시오.**

Physical(L1)은 비트를 신호로 변환하여 물리적으로 전송하고, Data Link(L2)는 MAC 주소로 인접 장치 간 프레임을 전달하며, Network(L3)는 IP 주소로 네트워크 간 라우팅을 담당한다. Transport(L4)는 포트 번호로 프로세스를 구분하고 TCP/UDP로 전송을 제어한다. Session(L5)은 세션 관리, Presentation(L6)은 데이터 형식 변환, Application(L7)은 애플리케이션 프로토콜을 제공한다.

**Q. MAC 주소와 IP 주소의 차이점은?**

MAC 주소는 L2 주소로 48비트, NIC에 하드웨어적으로 할당되어 같은 네트워크 내 인접 장치를 식별한다. 평면적이라 라우팅이 불가능하다. IP 주소는 L3 주소로 32비트(IPv4), 논리적으로 할당되며 네트워크+호스트 계층 구조로 라우팅이 가능하다. 패킷이 라우터를 통과할 때 MAC은 매 홉마다 바뀌지만 IP는 유지된다.

**Q. ARP란 무엇인가?**

IP 주소로 MAC 주소를 알아내는 프로토콜이다. IP 패킷을 전송하려면 이더넷 프레임이 필요하고 프레임에는 목적지 MAC이 필요하다. 목적지 IP에 대해 브로드캐스트로 ARP Request를 보내면, 해당 IP를 가진 호스트가 자신의 MAC으로 유니캐스트 Reply한다. 결과는 ARP 캐시에 저장하여 재사용한다.

**Q. TCP와 UDP의 차이점은?**

TCP는 연결 지향적이고 순서 보장, 재전송, 흐름/혼잡 제어를 제공하여 신뢰성 있는 전송을 보장한다. UDP는 비연결이고 이런 기능이 없어 신뢰성을 보장하지 않지만 오버헤드가 적고 빠르다. HTTP, 이메일 등은 TCP를, DNS 조회, 실시간 스트리밍, 게임 등은 UDP를 사용한다.

**Q. 웹 서버가 80번 포트 하나로 수만 개 연결을 처리할 수 있는 이유는?**

TCP 연결은 (출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port) 4-tuple로 식별된다. 서버 포트(80)는 같아도 각 클라이언트의 IP와 임시 포트가 다르므로 서로 다른 연결로 구분된다.
